# Database migrations

MySQL 8, one schema per environment (`imp`, `imp_test`). Webinar has its own schema, `imp_webinar`, managed by `services/webinar`.

```bash
npm run db:migrate        # from the repository root; applies every file not yet recorded
```

`src/core/migrate.ts` reads `*.sql` in filename order and records each applied file in `schema_migrations`. Tests apply the same files to `imp_test` before they run.

## Rules

1. **Never edit an applied file.** The runner skips it, so an edit would leave existing databases different from new ones. Add the next number instead.
2. **One purpose per file**, named `NNN_<module>_<topic>.sql` (three digits, no gaps; `platform`, `training`, `bdr`, ...). The module prefix matches the table prefix, so a module's history is one `ls *_bdr_*` away.
3. A file that changes data (backfills, counters) says so in a comment at the top.
4. MySQL commits DDL immediately, so a failed file can leave a partial change. Keep DDL statements idempotent where the engine allows (`IF NOT EXISTS`) and small enough to fix by hand.

## Conventions

| Topic | Rule |
| --- | --- |
| Tables | `snake_case`, prefixed with the module: `bdr_calls`, `training_scenarios`. Platform tables have no prefix |
| Ids | `CHAR(26)` ULID, generated by the API |
| Time | `DATETIME(3)`, UTC. The pool runs with `timezone: 'Z'` |
| Tenant | Every module table has `customer_id` and every query filters by it |
| Documents | A `*_json` column holds a form the API does not filter on. Anything filtered, joined or counted is a real column |
| Deletes | Soft delete with `deleted_at` (customers, users and the records people remove). Every list query filters `deleted_at IS NULL` |
| Keys | `fk_<table>_<ref>`, `idx_<table>_<purpose>`, `uq_<table>_<purpose>` |

## Map

| File | Owns |
| --- | --- |
| `001_platform_identity.sql` | `customers`, `users`, `user_modules` |
| `002_platform_tenancy.sql` | `customer_modules`, `audit_logs`; slug, plan and status on `customers`; profile, status and session version on `users` |
| `003_training_init.sql` | `training_personas`, `training_templates`, `training_scenarios`, `training_sessions` |
| `004_bdr_core.sql` | `bdr_campaigns`, `bdr_calls`, `bdr_meetings` (the CRM records) |
| `005_bdr_dialer.sql` | `bdr_leads`, `bdr_dial_attempts`, `bdr_telephony_settings`, `bdr_operator_extensions` (the auto-dial engine) |
| `006_bdr_calls_link.sql` | Links `bdr_calls` to attempt and lead, promotes qualification and callback to columns, links meetings through `call_id`, drops `bdr_campaigns.campaign_json` |
| `007_bdr_drop_unused.sql` | Drops `bdr_dial_attempts.provider_json` |
| `008_training_sessions_flow.sql` | Adds `persona_id`, `media_mode`, `ai_provider`, `judge_source` to `training_sessions`; creates `training_session_messages` (one row per message, unique `(session_id, seq)`); moves transcripts that older sessions kept inside `session_json` into that table |
| `009_bdr_call_summary.sql` | Adds the AI call summary to `bdr_calls`: `summary_text`, `summary_source`, `summary_status`, `summary_tries`, `summary_updated_at`, `transcript_text`. The summary built from the record is computed on read and not stored |

## How BDR tables relate

```
bdr_campaigns 1─┬─* bdr_leads 1─* bdr_dial_attempts *─1 users (operator)
                │                        │ 1
                │                        └─ 0..1 bdr_calls 1─* bdr_meetings
                └─* bdr_calls (campaign_id)
```

- `bdr_dial_attempts` is the telephony event: who dialed which lead, the provider result, the recording.
- `bdr_calls` is the attendance the operator saved after a connected attempt. `attempt_id` is unique, so an attempt is saved once.
- `bdr_campaigns.lead_count` and `completed_count` are derived from `bdr_leads`; nothing else writes them.
- `bdr_telephony_settings` is per customer (credentials encrypted); `bdr_operator_extensions` is per user.

## Seed data

`npm run seed -w @imp/api` creates development customers, users and the Treinamento IA starter catalog (the same one the customer administrator installs from the module). It never creates BDR rows and, in production, creates only the platform administrator.

## History

The files were renumbered by module once (`001_identity` → `001_platform_identity`, `002_training` → `003_training_init`, `003_bdr` → `004_bdr_core`, `004_bdr_dialer` → `005_bdr_dialer`, `005_tenancy_access` → `002_platform_tenancy`, `007_drop_unused_columns` → `007_bdr_drop_unused`). `RENAMED_MIGRATIONS` in `src/core/migrate.ts` rewrites the recorded names in existing databases, so none of them re-runs. Do not extend that map for new files.
